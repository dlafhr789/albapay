# 작업 규칙

커밋, 문서, 변경 기록을 이 규칙대로 남긴다. 사람과 코딩 에이전트 모두 같은 규칙을 따른다.

## 1. 커밋

### 형식

```
<type>(<scope>): <요약>

<본문: 무엇을 왜 바꿨는지>
```

| type | 쓰는 때 |
| --- | --- |
| `feat` | 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 동작이 바뀌지 않는 구조 변경 |
| `test` | 테스트만 추가·수정 |
| `docs` | 문서만 수정 |
| `build` | 의존성, 빌드 설정 |
| `ci` | CI 설정 |
| `chore` | 그 밖의 잡무 (저장소 설정 등) |

- scope는 `shared`, `api`, `web`, `infra`, `docs` 중 하나다. 여러 곳에 걸치면 생략한다.
- 요약은 한국어로 50자 이내, 끝에 마침표를 찍지 않는다. "~ 추가", "~ 수정"처럼 무엇을 했는지가 보이게 쓴다.
- 본문은 요약만으로 이유가 안 보일 때 쓴다. 무엇을 바꿨는지보다 왜 바꿨는지를 쓴다. 72자 근처에서 줄을 바꾼다.

예시:

```
feat(shared): 주휴수당 4주 이동 평균 판정 추가

주마다 근무 시간이 다르면 그 주만 보고는 15시간 요건을 판정할 수 없다.
그 주를 포함한 직전 4주의 계약 근무 시간을 평균내서 판정한다.
```

### 단위

- 커밋 하나에 논리적 변경 하나만 넣는다. "기능 추가 + 관련 없는 정리"는 두 커밋으로 나눈다.
- 모든 커밋에서 빌드와 테스트가 통과해야 한다.
- 동작이 바뀌는 커밋에는 테스트와 `CHANGELOG.md` 수정이 같이 들어간다.

### 브랜치와 PR

- `main`에 직접 커밋하지 않는다. 저장소 첫 설정 커밋만 예외다.
- 브랜치 이름은 `<type>/<짧은-설명>`이다. 예: `feat/weekly-holiday-pay`
- PR 제목은 커밋 형식과 같다. 본문에는 무엇을, 왜, 어떻게 확인했는지 쓴다.
- 병합은 Squash and merge로 한다. `main`의 커밋 하나가 PR 하나가 되게 한다.

### 커밋하면 안 되는 것

- 실제 근무·급여 기록, 개인의 보험 가입 상태 같은 개인 정보
- `.env*`, `*.tfstate*`, `*.tfvars`, 토큰, 캘린더 구독 URL, AWS 계정 ID
- `.private/`, `CLAUDE.local.md`

커밋 전 훅(`.githooks/pre-commit`)이 일부를 막지만, 훅에 기대지 않고 커밋 전에 `git status`로 직접 확인한다. 훅은 클론한 뒤 한 번 켜야 동작한다.

```
git config core.hooksPath .githooks
```

## 2. 문서

### 어디에 무엇을 쓰나

| 문서 | 내용 | 고치는 때 |
| --- | --- | --- |
| `README.md` | 소개, 스크린샷, 아키텍처 요약, 실행·배포 방법 | 사용자가 보는 기능이 바뀔 때 |
| `docs/architecture.md` | AWS 구성과 요청 흐름 | 리소스나 흐름이 바뀔 때 |
| `docs/deploy.md` | 배포 절차와 운영 명령 | 배포 방법이 바뀔 때 |
| `docs/payroll-rules.md` | 급여 계산 규칙과 테스트 케이스 | 계산 로직이 바뀔 때 |
| `docs/data-model.md` | DynamoDB 키 설계와 접근 패턴 | 저장 구조가 바뀔 때 |
| `docs/api.md` | 엔드포인트, 요청·응답 형식 | API가 바뀔 때 |
| `docs/decisions/` | 설계 결정 기록(ADR) | 결정을 내리거나 뒤집을 때 |
| `CHANGELOG.md` | 날짜별 변경 기록 | 동작이나 설계가 바뀌는 모든 변경 |
| `AGENTS.md` | 코딩 에이전트용 작업 지침 | 규칙이나 구조가 바뀔 때 |

아직 없는 문서는 해당 코드를 처음 만들 때 같이 만든다. 없는 코드를 설명하는 문서를 미리 쓰지 않는다.

### 쓰는 방식

- 첫 문장에 결론을 쓴다. "이 문서는 ~를 설명한다"로 시작하지 않는다.
- 숫자와 이유를 구체적으로 쓴다. "빠르고 안전한 구조" 대신 "Lambda URL은 CloudFront가 서명한 요청만 받는다"처럼 쓴다.
- 하지 않은 것과 한계를 적는다.
- 이모지 제목이나 "주요 기능" 같은 템플릿 문구를 쓰지 않는다.
- 흐름이나 구성처럼 구조가 있는 내용은 Mermaid 다이어그램으로 그린다. GitHub에서 그대로 보인다.
- 예시 데이터는 가상 데이터만 쓴다.
- 문서는 코드와 같은 커밋에서 고친다. 코드와 문서가 다르면 문서를 고친다.

### ADR 형식

파일 이름은 `docs/decisions/NNNN-짧은-설명.md`이고, 설명은 영문 kebab-case로 쓴다.

```markdown
# NNNN. 제목

- 상태: 채택 | 대체됨(NNNN) | 폐기
- 날짜: YYYY-MM-DD

## 상황

무엇을 정해야 했고, 어떤 제약이 있었나.

## 검토한 선택지

- A: 장점, 단점
- B: 장점, 단점

## 결정

무엇을 골랐고 왜 골랐나.

## 결과

이 결정 때문에 생기는 제약, 감수한 것, 다시 검토할 조건.
```

채택한 ADR은 내용을 고치지 않는다. 결정이 바뀌면 새 ADR을 쓰고, 기존 ADR의 상태만 `대체됨(새 번호)`로 바꾼다. 그래야 결정이 바뀐 과정이 남는다.

## 3. 변경 기록

"나중에 뭐 했지?"는 세 곳에서 찾는다.

| 질문 | 볼 곳 |
| --- | --- |
| 언제 무엇이 바뀌었나 | `CHANGELOG.md` |
| 왜 그렇게 정했나 | `docs/decisions/` |
| 코드가 정확히 어떻게 바뀌었나 | git 기록과 PR |

### CHANGELOG 쓰는 법

- 날짜별로 묶고 최신 날짜를 위에 둔다. 같은 날의 변경은 한 항목에 모은다.
- 분류는 추가, 변경, 수정, 삭제, 문서, 인프라 중에서 고른다.
- 한 줄에 무엇을 바꿨는지와 왜 바꿨는지를 쓴다. 관련 ADR이나 PR 번호가 있으면 붙인다.
- 계산 결과가 달라지는 변경은 "변경"에 쓰고 전후 차이를 적는다.
  예: "주휴수당 귀속 기간을 주 마지막 날 기준으로 변경. 월말에 걸친 주의 금액이 다음 달 정산으로 이동"
- 진행 중인 작업은 맨 위 `진행 중`에 적고, 끝나면 그날 날짜 항목으로 옮긴다.
